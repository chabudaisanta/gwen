# gwen ライブラリ整備

`gwen` のモジュール追加、既存実装の移植、機能修正、関連ドキュメント・検証の整備に使用する。リポジトリ直下の `AGENTS.md` を最優先の規約とする。

## 作業範囲

- 実装は `include/gwen/` 配下の適切な `.hpp` に置く。ライブラリはヘッダーオンリーとして維持する。
- 新規実装・移植では、Google Test を `test/unit/`、Verify を `verify/`、文書を `doc/` に必ず追加する。
- Verify は Library Checker、AOJ、yukicoder の問題だけを使用する。AtCoder を含むその他のジャッジは追加しない。
- 文書を追加・変更したら、`.verify-helper/docs/index.md` の目次にも必ず登録する。
- ビルド成果物は `.build/`、一時ファイルと作業記録は `temp/` を使用し、完了時に一時ファイルを残さない。

## 実装規約

- データ構造のクラス・構造体は PascalCase、代数構造の定義は snake_case を使う。
- 公開 API のメソッド、変数、関数、Concept は snake_case にする。Concept 名に `_concept` を付けない。
- 公開 API には `@brief`、必要に応じて `@tparam`・`@param`・`@return` を含む Doxygen コメントを付ける。
- グラフ・代数構造などの汎用コンポーネントには C++23 `concept` による厳密な型制約を設ける。
  - **概念を表すコンセプトを定義すること**: 代数構造（`monoid`, `abel`, `semiring`, `ring`, `field` 等）やグラフ理論（`graph`, `edge` 等）のような本質的な「概念」を表す場合にのみ定義する。
  - **適用可否チェッカーの禁止**: 単にある特定の関数や構造体に渡せる（適用できる）という意味合いだけのアドホックなコンセプト（`xxx_value`, `xxx_graph`, `xxx_weight`, `xxx_action` 等）は作らない。標準コンセプト（`<concepts>`）や通常のテンプレート引数で受ける。
- プリミティブ型をできるだけ避け、`gwen/types.hpp` の `i32`、`i64`、`usize` などを使用する。
- Verify の modint は原則 gwen 実装を使い、必要なら `USE_ACL_MODINT 0` で切り替える。
- ドキュメントは AC Library スタイルとし、各 API のメソッド名、**制約**、**計算量**を明記する。

## 新規実装・移植の必須フロー

1. `temp/` に作業記録を作る。設計、対象パス、公開 API、Concept、計算量、依存関係、単体テスト、Verify、文書の計画を記録する。
2. `code_reviewer` サブエージェントに作業記録の事前レビューを依頼する。命名、Concept、Doxygen、テスト・Verify・文書計画を確認させ、指摘は解消する。
3. 事前レビュー済みの仕様をユーザーに示し、実装開始の承認を得る。承認前に実装ファイルを変更しない。
4. 承認後に実装、単体テスト、Verify、文書、目次を追加・更新する。
5. WSL 経由でビルドと対象テストを実行する。失敗は自力で修正し、成功するまで繰り返す。
6. `code_reviewer` サブエージェントに実装全体の事後レビューを依頼する。指摘を解消し、必要なテストを再実行する。
7. `git diff` と作業ツリーを確認して、生成物・一時ファイルを取り除く。ユーザーへ変更内容と検証結果を日本語で報告し、承認済みなら Conventional Commits 形式でコミットする。

## 修正・保守のフロー

既存モジュールのバグ修正や文書修正では、影響範囲を先に調べる。新規実装・移植に当たらない小規模修正は、事前承認フローを省略してよい。ただし、関連テストを追加または更新し、変更後に実行する。公開 API、アルゴリズム、型制約、検証対象、文書に影響する変更は、上の必須フローを適用する。

## 検証

- プロジェクトの既存 CMake 手順を確認し、`.build/` を使用してビルドする。
- Google Test は変更箇所に対応するテストを実行する。
- Verify は対応サービスの問題に対して実行可能な状態にする。
- 実行コマンドは Windows 側から直接 Linux コマンドを実行せず、`wsl -e sh -c "…"` を経由する。

## レビュー依頼の要点

事前レビューでは設計が規約を満たし（特に不要なアドホックコンセプトを作っていないか確認）、テスト・Verify・文書が不足しないか確認させる。事後レビューでは差分全体を対象に、正しさ、境界条件、命名、Doxygen、Concept、計算量、テスト網羅性、Verify のジャッジ制約、文書と目次の整合性を確認させる。承認または具体的な修正点を明示するよう依頼する。

## 完了条件

- 対象の実装と公開 API が規約どおりである。
- 必要な Google Test、Verify、文書、目次がそろっている。
- 関連テストが成功し、事後レビューの指摘が残っていない。
- 作業ツリーに `.build/` や `temp/` の生成物を残していない。
